# TBC Bank UI Test Automation

Java + Selenide + TestNG UI regression project for https://www.tbcbank.ge.

## 1. Automated scenarios

The project contains exactly five automated scenarios, with exactly two coming from Locations functionality as required by the assignment.

| # | Scenario | Class |
|---|---|---|
| 1 | Main navigation works on desktop and mobile | `HomepageNavigationTest` |
| 2 | Locations can be filtered to branches | `LocationsFilterTest` |
| 3 | Locations can be filtered to ATMs | `LocationsFilterTest` |
| 4 | Loan amount changes the monthly payment estimate | `LoanCalculatorTest` |
| 5 | Money transfer page loads its main content | `MoneyTransferPageTest` |

The navigation scenario contains the required meaningful mobile/desktop difference: desktop checks visible navigation items while mobile opens the burger menu first.

## 2. Execution profiles

- Desktop: `1440x900`
- Mobile: `390x844`
- Profiles are supplied by `testng.xml`; test source code does not need to change.
- `parallel="tests"` runs the Desktop and Mobile TestNG blocks in parallel.
- Each test method creates its own `SelenideDriver`, so desktop and mobile configuration is not shared through Selenide's static browser API.

Run:

```bash
mvn clean test
```

Optional debugging:

```bash
mvn clean test -Dheadless=false
```

## 3. Why automate this?

### Navigation
Risk: users can be blocked from reaching important products if navigation fails.

Business value: navigation is a high-use entry point and a good regression target.

Why automate: the same navigation flow can be checked quickly on every run.

### Locations filters
Risk: users may be shown the wrong location type when looking for a branch or ATM.

Business value: finding a physical banking location is a direct customer journey.

Why automate: filter selection is repetitive and easy to regress.

### Loan calculator
Risk: a broken input or calculation display can give customers misleading information.

Business value: the calculator supports customers evaluating a loan.

Why automate: input/output behavior is deterministic and suitable for regression automation.

### Money transfers
Risk: a broken information page can prevent customers from understanding available transfer services.

Business value: money transfers are a core banking journey.

Why automate: page availability and essential content are inexpensive to verify repeatedly.

## 4. Selector strategy

1. Accessible attributes such as `aria-*`, `alt`, `role`, `type`, and `name` are preferred because they describe the element's purpose.
2. Stable URL fragments such as `href*='atms'` are used where navigation destination is the important behavior.
3. Visible text is used for user-facing navigation and filter controls.
4. Partial class matching is used only as a fallback for components where no stable semantic attribute is available.
5. Bare structural elements such as `h1` and `main` are used only for page-level landmarks.

A selector can still require adjustment if the live site changes its DOM or localization. The final selectors should be confirmed in Chrome DevTools before CI execution.

## 5. Flaky test awareness

The loan calculator is the main flakiness risk because its result can be updated asynchronously after input. The test uses Selenide's polling waits instead of `Thread.sleep`, and it waits until the result differs from its original value.

The project also avoids sharing a mutable Selenide browser configuration between parallel profiles by creating an independent `SelenideDriver` for each test.

## 6. Mobile is not desktop

The navigation test intentionally checks different behavior. Desktop expects the main navigation items to be directly visible. Mobile expects a burger-menu control and opens it before checking the navigation. This is a real interaction difference rather than only a viewport-size assertion.

## 7. Deliverables not generated by automation

Zephyr Scale scenarios and bug reports require actual manual exploration and evidence from the live site. They should be created separately with screenshots/video evidence, including at least one bug verified at `390x844`.
